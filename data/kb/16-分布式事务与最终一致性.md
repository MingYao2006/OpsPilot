# 分布式事务与最终一致性

## 方案选型

按业务对一致性的真实要求选型，不要一律上强一致方案：

| 场景 | 方案 | 一致性 | 失败处理 |
|---|---|---|---|
| 下单扣减库存 | TCC | 准实时一致 | Cancel 补偿 |
| 支付结果通知 | 本地消息表 | 最终一致 | 定时重试 |
| 积分与优惠券发放 | 事务消息 | 最终一致 | 对账冲正 |
| 跨库实时统计 | 不做分布式事务 | 允许延迟 | 走离线数仓 |

## 幂等要求

所有写接口必须携带全局唯一 `biz_no`，去重表按 `biz_no` 建唯一索引，保留 7 天。
重复请求直接返回首次执行结果，不得重复扣款、重复发货。
幂等表清理任务每天 03:00 执行，单批删除 5000 行，避免长事务。

写接口的状态流转必须单向：待支付 → 支付中 → 成功/失败，禁止逆向流转。
状态更新使用乐观锁（version 字段），更新影响行数为 0 时视为并发冲突并重读重试，最多 3 次。
跨服务的状态变更通过事务消息投递，本地事务与消息发送必须在同一个数据库事务内提交，
投递失败由定时任务每 30 秒扫描本地消息表补偿，单表积压超过 1000 条即告警。

## 重试与对账

- 重试 6 次，退避间隔 1s / 5s / 30s / 2m / 10m / 30m，6 次后进入死信队列人工处理。
- T+1 对账以支付渠道流水为准，金额差异超过 0.01 元或笔数差异不为 0 立即告警。
- 冲正窗口为 24 小时，超过窗口的差异只能走人工补单，不允许自动改写历史流水。

对账任务每天 04:00 启动，先跑逐笔比对，再跑汇总比对，两者结论不一致时以逐笔结果为准。
单次对账数据量超过 500 万笔时按渠道分片并行，分片数 8，单分片超时 20 分钟。
差异记录写入差异表并生成工单，工单必须当日闭环，不允许跨天挂起。
人工补单需双人复核并记录操作人、时间与原因，补单接口本身也必须幂等。

## 悬挂与空回滚

TCC 的两个经典异常必须显式处理：

1. **空回滚**：Cancel 早于 Try 到达，需记录空回滚标记，否则后续 Try 会被误判为重复提交。
2. **悬挂**：Try 在 Cancel 之后到达，需在 Try 阶段先查防悬挂表，命中则直接拒绝。

两个标记表都以事务 ID 为主键，TTL 设为 24 小时，与冲正窗口对齐。
补偿事务的执行顺序必须与 Try 的提交顺序相反，Cancel 自身也要带重试，重试 3 次后转人工。
所有事务参与者都必须实现查询接口，供补偿前确认状态使用，未实现查询接口的服务不允许接入。

## 常见误判

看到"最终一致"就认为中间态可以随便暴露。用户在下单后 3 秒内刷新页面，
若订单仍处于处理中却直接提示失败，会触发重复下单。
正确做法是展示"处理中"并轮询，而不是把未完成当作失败回滚。
