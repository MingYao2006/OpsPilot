# 慢SQL治理与索引优化

## 慢SQL判定与采集

慢日志阈值 `long_query_time = 1` 秒，超过 5 秒单独打标。采集链路：慢日志 → Filebeat → ClickHouse，保留 90 天。每日 09:00 出 Top 50 报告，按「总耗时 = 平均耗时 × 执行次数」排序，而不是只看单次最慢。

| 耗时区间 | 分级 | 处理时效 |
|---|---|---|
| 1 ~ 3 秒 | 观察 | 7 天内优化 |
| 3 ~ 10 秒 | P3 | 3 天内优化 |
| 10 ~ 30 秒 | P2 | 24 小时内优化 |
| 大于 30 秒 | P1 | 4 小时内处置，必要时先杀会话 |

单实例慢SQL 每分钟超过 20 条触发告警；超过 100 条按 P1 处理并考虑限流降级。

每条慢SQL 按「库名 + 表名 + SQL 指纹」聚合，指纹相同的视为同一条，避免因参数不同被拆散。报表类 SQL 与在线类 SQL 分开统计，报表慢不升级为线上故障，但必须纳入季度优化计划。

## 索引设计规范

- 联合索引遵循最左前缀，区分度高的列放左侧；区分度 = 不重复值 / 总行数，低于 0.1 的列不单独建索引。
- 单表索引数量不超过 5 个，单索引字段不超过 4 个，避免索引膨胀拖慢写入。
- 禁止在索引列上使用函数、隐式类型转换与 `LIKE '%x'`；范围查询列之后的字段无法走索引。
- 深分页改为游标：`WHERE id > ? ORDER BY id LIMIT 100`，禁止 `LIMIT 100000, 20`。
- 大表（超过 2000 万行）加索引必须用 Online DDL 或 gh-ost，且限制在低峰期（01:00–05:00）执行。

索引评审由 DBA 与业务方共同完成，业务方需说明查询模式与数据增长预期，只提交 SQL 不说明用途的申请直接驳回。

## 典型改写

| 反模式 | 改写方式 | 预期收益 |
|---|---|---|
| `SELECT *` | 只取需要的列 | 减少 30%~60% IO |
| 子查询 IN | 改 JOIN 或 EXISTS | 常见提速 5 倍以上 |
| OR 条件跨列 | 改 UNION ALL | 命中索引 |
| 大事务批量更新 | 拆成每批 500 行 | 降低锁等待 |
| 无 WHERE 统计 | 走预聚合表 | 从秒级降到毫秒级 |

改写后必须在预发用真实数据量验证，禁止只看执行计划就上线。优化效果以 P99 为准，单次耗时下降但执行次数上升的不算优化。

## 执行计划核查

上线前必须 `EXPLAIN`，关注三项：`type` 不得为 `ALL`，`rows` 估算不超过 10 万，`Extra` 不得出现 `Using filesort` 与 `Using temporary`。SQL 审核平台对不达标语句直接拦截，白名单需 DBA 审批。

索引变更同样走发布流程，先在从库验证再上主库；删除索引前先观察 7 天，确认 `sys.schema_unused_indexes` 中确实无使用记录。

主从延迟超过 5 秒时，禁止把报表查询打到从库；超过 30 秒必须切回主库并告警。

连接层也要设限：单实例最大连接数 1000，应用侧连接池上限 200，单条 SQL 最长执行 10 秒由 `max_execution_time` 强制中断。大表结构变更与数据归档错峰执行，历史数据保留 13 个月，超期数据先归档到冷存储再删除，单次删除不超过 1 万行，删除后观察从库延迟 10 分钟再继续下一批。

## 常见误判

看到数据库 CPU 打满**不要**先加索引或加从库。CPU 高常常是某条 SQL 执行次数暴涨（例如缓存击穿导致回源），先看慢SQL 的执行次数趋势与 QPS 变化；执行次数正常而单次耗时上升，才考虑执行计划劣化或数据量增长。
