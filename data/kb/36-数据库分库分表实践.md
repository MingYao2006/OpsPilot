# 数据库分库分表实践

## 分片键选择

用户中心按 `user_id` 取模分片，共 8 库 64 表，即每库 8 张表。分片键一旦确定不可更改，选型必须满足三个条件：高基数、分布均匀、且出现在 95% 以上的查询条件中。

禁止用作分片键：`order_id`、`create_time`、`status`（基数低或时间倾斜）。订单类查询必须带 `user_id`，否则走异构索引表 `idx_order_user`，该表只存 `order_id → user_id` 映射，延迟容忍 3 秒。

历史数据归档与分片解耦：单表行数超过 2000 万行时启动归档，把 12 个月以前的数据搬到归档库，归档任务限速 3000 行/秒，只允许在 01:00-06:00 执行，禁止在业务时段做批量删除。归档后必须执行一次行数核对，归档前后总行数必须一致。

## 路由与查询约束

| 查询类型 | 是否允许 | 处理方式 |
|---|---|---|
| 带 user_id 精确查 | 允许 | 直接路由到单库单表 |
| 带 user_id + 时间范围 | 允许 | 单库单表范围扫描 |
| 不带分片键 | 禁止 | 拒绝并报错，不降级为全库扫描 |
| 跨分片聚合 | 受限 | 仅允许统计类，走离线宽表 |
| 跨分片 JOIN | 禁止 | 改为应用层拼装 |

全库扫描是最高危操作，8 库并发扫描会瞬间打满连接池。网关层对无分片键的 SQL 直接拦截，返回 `400 MISSING_SHARD_KEY`。

## 扩容与数据迁移

从 8 库扩到 16 库采用**双写 + 全量迁移 + 增量追平 + 灰度切读**四步：

1. 双写开启，观察 24 小时，双写失败率必须为 0。
2. 全量迁移按分片串行执行，单分片限速 5000 行/秒，避免打满 IO。
3. 增量追平，延迟需稳定在 1 秒以内并持续 30 分钟。
4. 灰度切读按 1% → 10% → 50% → 100% 推进，每档观察 30 分钟。

迁移期间禁止执行 DDL，禁止在业务高峰期（10:00-12:00、19:00-22:00）做切读。

## 分片后的典型问题

- **热点分片**：单分片 QPS 超过其他分片 3 倍即告警。大客户单独拆到独立分片，不参与取模。
- **分布式事务**：跨分片写一律走本地消息表 + 最终一致，禁止使用强一致两阶段提交。
- **全局唯一 ID**：使用号段模式，单次取 1000 个，号段余量低于 20% 时异步预取下一段。

分片表的建表语句由统一工具生成，禁止手工建表，避免 64 张表结构漂移。每周执行一次表结构一致性校验，发现差异立即告警。- **分页深翻**：禁止 `LIMIT 100000, 20`，改为基于 `user_id` 游标翻页。

分片元数据（库表映射、路由规则）统一存放在配置中心，版本号与配置变更绑定，路由规则变更必须全量实例生效后才能执行数据迁移。迁移期间新旧路由规则并存，通过影子表比对两边数据，差异行数必须为 0 才允许推进下一阶段。

## 常见误判

**不要因为慢查询告警就去加索引或改分片数。** 分库分表后的慢查询有 80% 来自「未带分片键导致的全库扫描」或「跨分片排序」，这两类问题加索引无效。先看执行计划里是否出现多库并发，再决定处置方向。贸然新增索引会拖慢写入，且 DDL 在 64 张表上串行执行可能耗时数小时。
